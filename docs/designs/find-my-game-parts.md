# Design: Find My Game Parts — Board Game Replacement Parts (Demand-Capture MVP)

Generated by /office-hours on 2026-09-23
Branch: main
Repo: local only, no remote configured yet
Status: APPROVED
Mode: Startup

## Problem Statement

Top-tier hobbyist board games are expensive ($80-200+), have hundreds of components (e.g. LOTR: Fate of the Fellowship has 169 cards + 163 other components), and manufacturers rarely restock or sell individual replacement parts. When a piece goes missing, the game can become literally unplayable. The founder wants to build a business around sourcing and reselling individual replacement components for these games — either by buying games (used-incomplete or new) to part out, or by running a peer-to-peer clearinghouse that connects people who have spares with people who need them.

## Demand Evidence

- Founder personally paid ~$10 (card + shipping) to replace a lost card in LOTR: Fate of the Fellowship via an active BGG marketplace thread (https://boardgamegeek.com/thread/3565859) that remains active with other users requesting parts for the same game.
- Landscape research confirmed this isn't an isolated case: BoardGameGeek maintains its own curated "Spare Parts Resources List" directory because the space is served by many small, fragmented sellers (individual eBay sellers, Custom Game Bits, Board Game Beast, "Bits & Bobs," The Big Game Hunter, Board Games R Us) with no dominant player.
- Publisher behavior is a real, trackable signal: Asmodee stopped providing direct replacement parts in 2025 (pushing customers to a retailer-based system), widening the third-party opportunity. Stonemaier Games is the opposite extreme — spent $43K/year shipping free replacement parts for only 9 games — meaning Stonemaier titles are bad targets for this business.
- Explicitly acknowledged as thin: this is founder-as-customer-zero plus one active forum thread, not validated market-wide demand. That's exactly what the MVP is designed to test.

## Status Quo

No single or good solution exists today. Workarounds observed/lived by the founder:
- Home-printing and laminating a replacement card (poor quality, wrong look/feel vs. the original).
- 3D-printing replacement meeples/tokens, or requesting them from other hobbyists who own a 3D printer.
- Searching BGG/Reddit forum threads and hoping another owner has a spare to sell — slow, low-trust, inconsistent.
- Manufacturers rarely have a replacement-parts program at all (Stonemaier is a notable, generous exception).

## Target User & Narrowest Wedge

**Target user:** Founder-as-customer-zero — a passionate hobbyist board gamer who spends real money on complex, expensive games (often crowdfunded via Kickstarter/Gamefound), part of the post-COVID boom in tabletop hobbyism (conferences, YouTube influencers, the documentary "The Hobby"). This person treats a single missing unique component as making an $80-200 game literally unplayable, versus losing one of thirty duplicate meeples being a mere annoyance — a criticality-tier distinction the founder identified that neither outside AI model surfaced.

**Narrowest wedge (final, after iteration):** A concierge MVP, not a catalog. No parts taxonomy, no founder-side stock-quantity tracking, no automation:
- Founder marks which **games** (not parts) are in inventory — coarse-grained, binary.
- Buyers can request a part from **any** BGG game, owned or not, freeform text, no pre-built catalog — this captures demand for titles not yet acquired, feeding the future "critical mass → buy this game" decision. Buyers do state how many units they need (buyer-side demand signal — see Recommended Approach); what's deferred is the founder tracking exact stock counts on hand.
- Founder manually checks physical inventory per request and replies yes/price or no.
- Founder-side stock-quantity tracking and a "known not available" cache are explicitly deferred until request volume makes manual rechecking tedious — not built on day one.

## Constraints

- Auth: OIDC/OAuth 2.0 via self-hosted Keycloak. Public browsing (no auth) for inventory; auth required to submit a request; admin (founder) role required to add inventory. Must support username/password as a first-class path (not just Google/Facebook), with a clear sign-up flow.
- Admin inventory-add form uses the BoardGameGeek API for game lookup.
- Messaging must make it clear why a user would request a game not currently in inventory ("Let me know if there's a game you need parts for, even if I don't currently have it available. If enough people need parts, I'll get it.")
- UI: playful, retro/8-bit-adjacent aesthetic crossed with old-Google-homepage minimalism; must include an easy, visible accessibility toggle (high contrast / large text) for sight-impaired users; must support a cosmetic theme system (selectable regardless of login state, persisted via cookie) with all four schemes (Parchment, Arcade Night, Seafoam, Mono). **(Reversed 2026-09-26 — founder decision):** the eng review's scope trim to ship only Parchment at v1 was undone post-launch; all four themes shipped together since the picker itself was cheap enough that deferring the other three wasn't worth the scope-discipline cost.
- Automation (taxonomy, quantity tracking, gig-worker fulfillment routing, auto-purchase triggers) is the founder's long-term vision but is explicitly deferred past the MVP — the MVP's job is to validate demand cheaply, not to build the full vision.

## Premises

1. Core pain is real and recurring, evidenced by the founder's own paid transaction, an active BGG thread, and a whole ecosystem of small ad hoc sellers plus BGG's own supplier directory.
2. The market is fragmented, not empty — no dominant, systematic player exists yet. The opportunity is consolidation, not first-mover entry into a vacuum.
3. Publisher policy is a critical per-title variable to track: publishers retreating from replacement programs (Asmodee) are good targets; publishers with generous free-replacement programs (Stonemaier) should be avoided.
4. The unit economics are an unverified assumption, not a data point — zero parts sold to date. The "$60 in → ~$500 gross" napkin math has not been tested against real buyers.
5. **(Revised during session)** Viability depends on demand density per component, weighted by supply-per-purchase for that component's criticality tier — not simply "operations/software first." Unique components (one-of-a-kind cards) get exactly 1 unit of supply per game purchased, so the price-per-unit must justify the cost of acquiring a copy; fungible components (e.g. 30 duplicate meeples) get many units per purchase, so cumulative demand across many buyers over time — not repeat demand in a single transaction — is what matters. This distinction was the founder's own correction to both outside AI models' framing and is the sharpest insight of the session.

## Cross-Model Perspective

Two independent second opinions were run (Claude subagent, then Codex/gpt-6-sol after a CLI upgrade). Both converged independently on the same core recommendation before the founder's criticality-tier refinement:

- **Claude subagent:** Steelmanned the idea as a "demand-routing layer" for missing parts, not an inventory business. Flagged the founder's own quote — "people will search on forums like bgg or reddit for help" — as the most revealing answer, showing the real pain is discovery/matching, not part scarcity. Challenged premise #5 (ops/software-first), arguing demand density per SKU is the real unverified variable. Proposed a 48-hour, zero-inventory "demand-capture board" prototype (Next.js + Postgres, BGG API, request form, no payments/inventory/taxonomy). Flagged a real legal risk: reselling original parts is covered by first-sale doctrine, but printing/reproducing components for sale is not.
- **Codex (gpt-6-sol):** Independently reached the same conclusion — build a request-and-match prototype before buying inventory, because "repeat demand and profitable fulfillment are the assumptions that determine whether inventory automation is worth building." Proposed a nearly identical stack (Next.js + Supabase, BGG API).
- **Founder's refinement, post-second-opinions:** Both outside models treated "demand needs to repeat on the same part" as a single variable. The founder correctly split this by criticality tier (see Premise #5) — a distinction sharper than either outside model produced independently, and the basis for the final MVP design.

## Approaches Considered

### Approach A: Demand+Supply Capture MVP (no inventory bought) — chosen, then simplified further
No inventory bought upfront. Web app with a request form (BGG game lookup, freeform part, quantity, max price) and a supply-listing form. One trial purchase, seeded into real BGG/Reddit threads, fulfilled by hand. Effort: S (revised — see the Keycloak feasibility note under Recommended Approach; auth setup adds real time on top of the app itself). Risk: Low.

### Approach B: Full Systematized Platform
Build the original full vision immediately: taxonomy with criticality tiers, publisher-policy overlay, demand-triggered purchasing, real inventory/quantity tracking, gig-worker fulfillment routing. Effort: XL. Risk: High — builds deep automation on top of still-unverified unit economics. Rejected for now: classic "solution before validation" trap.

### Approach C: Peer-to-Peer Clearinghouse
Never buy games; match people with spares to people who need parts, taking a fee (eBay-style). Effort: M. Risk: Medium. Rejected for the MVP: loses the multiplied-unit economics of buying a game with many duplicate components (e.g. 30 meeples from one $60 purchase), and requires two-sided liquidity at cold start.

## Recommended Approach

**Approach A, refined to a true concierge MVP** (the founder's own simplification, sharper than the original three-option framing):

- **Public (no auth):** browse which games are in inventory (game-level only, not part-level).
- **Authenticated (Keycloak OIDC — email/password as primary, Google + Facebook as secondary):** submit a request for any BGG game (via BGG API lookup, with manual free-text game-name entry as a fallback if the lookup fails or is slow — see Dependencies). Fields: freeform part description, **buyer-requested quantity** (e.g. "3x Shadow Troop meeples" — retained; this is buyer-side demand signal, not founder-side stock tracking, and is required input for the criticality-tier demand analysis in Success Criteria), **edition/printing note (freeform, optional — added per eng review's outside voice)**: a BGG game entry doesn't distinguish edition, language, or printing, and a part from the wrong printing may not physically fit; this optional field lets a buyer flag it without building real edition tracking, and **max you'd pay (optional)**. Quantity and max-price are retained from Approach A's original form and appear in the approved wireframe; the edition/printing note is new. Copy: *"missing a piece? We may have it. Or, we can get it."* (tagline) and *"Let me know if there's a game you need parts for, even if I don't currently have it available. If enough people need parts, I'll get it."* (no-match callout) — both ship as-is in the UI.
- **Admin (founder, authenticated + admin role):** add a game to inventory via BGG API lookup (with the same manual fallback); **toggle a game's availability on/off** (mark unavailable/remove from the public list, not just add) as stock is depleted — **toggling off does not touch already-pending requests for that game; the admin resolves them manually on the same triage list (decided per eng review — no auto-rejection)**; view incoming requests **as a simple datestamp-ordered list per game**, tagged unique/fungible per request (dropdown, manual, no automatic classification). There is no automatic grouping of freeform text into per-part buckets — the founder reads the chronological list and uses judgment to recognize when multiple requests describe the same physical part. For scarce/unique parts (supply of 1 per game owned), **the earliest-dated request wins** when fulfilling, **with a 5-day claim window (added per eng review's outside voice — the original plan had no expiry): if the earliest requester doesn't confirm and pay within 5 days of being notified, the claim passes manually to the next-earliest pending request for that part.** Demand-density signal (dense vs. thin per part/tier) is read manually off the same chronological list, not computed as an aggregate count. Manually respond to each request (available + price, or not available). **After marking a request "available," the admin view shows other pending requests for the same game with a one-click "mark not available" action (added per eng review) — a nudge against double-approving the same physical part across two requests; it does not prevent a true simultaneous double-approval in two browser tabs at once, only the more common forget-later case.**
- **Buyer notification:** when the founder responds to a request, the buyer is notified by **email** (simple transactional email — no in-app status page for v1).
- **Payment:** collected manually for the MVP (e.g. a PayPal or Venmo request sent alongside the founder's reply) — no integrated payment processor at this stage.
- **Explicitly deferred to v2+:** full parts taxonomy, founder-side stock-quantity tracking, "not available" cache, gig-worker fulfillment, automated purchase triggers. Physical inventory checks per request are the source of truth until volume makes that untenable.
- **UI:** retro/8-bit-meets-old-Google aesthetic. All four color schemes (Parchment, Arcade Night, Seafoam, Mono) plus the high-contrast/large-text accessibility toggle shipped together (see reversal note under Constraints). Wireframe approved and saved at `docs/designs/assets/find-my-game-parts-wireframe/sketch.html` (and `sketch.png`).
- **Working title:** "Find My Game Parts" (domain undecided — see Open Questions).

**Sequencing (revised — founder decision, 2026-09-24):** originally scoped as strictly sequential (Assignment first, app only after signal). The founder chose to run them in parallel instead: a real working URL is a stronger post than a bare form, and posting requires having a copy of the game to point people at anyway. The build trigger below still governs whether the *automation and taxonomy deferred to v2+* gets built — it does not gate this MVP's construction anymore.

**Build trigger (added per eng review — outside voice flagged this as undefined):** originally: build the concierge app once the Assignment reaches **10+ distinct requests, or 3+ people who state a real max-price they'd pay, within 4 weeks of the Assignment going live**. Superseded by the parallel-build decision above — kept here as the number that still validates whether Premise #4/#5 (unit economics, demand density) hold, independent of when the code gets written.

This directly tests the two things that are actually unverified (per-tier demand density, real willingness-to-pay net of shipping/labor) with minimal cash risk (one game purchase, no engineering investment in taxonomy or automation) before committing to Approach B's automation bet or Approach C's fee-only model.

## Open Questions

- **Demand density per criticality tier is still unmeasured.** Need real request volume against the MVP to know whether unique-part willingness-to-pay and fungible-part cumulative sell-through actually clear the cost of acquiring games plus labor/shipping.
- **Domain/brand name is undecided.** Candidates discussed: `games.parts` (shortest, most naturally spoken), `parts.games`, `partsfor.games`, `findmygame.parts` (longer but names the MVP's exact action and doubles as a tagline). No rush to register; "Find My Game Parts" is the working title in the UI for now. Worth a trademark/availability check before committing.
- **Keycloak self-hosted vs. hosted auth (Supabase Auth/Auth0/Clerk).** Founder has decided on self-hosted Keycloak; flagged once as more ops overhead than a hosted alternative for an unvalidated MVP, but this is the founder's explicit choice. **Timeline risk (added per review):** hosting, TLS, and IdP app registration/consent screens for Google + Facebook is real setup work not yet budgeted against the "few weeks" target in Success Criteria — if that setup slips, it delays the concierge MVP but does not block the Assignment's no-code landing page, which runs independently first.
- **When to introduce quantity tracking and the "not available" cache** — deferred until manual physical-inventory rechecking becomes a bottleneck, not built at launch.
- **IP/legal risk for reproduced components** (flagged by the Claude subagent): reselling an original physical part is covered by first-sale doctrine; printing/reproducing copyrighted/trademarked artwork for commercial sale is not the same and was not analyzed further in this session.
- **Keycloak is a single point of failure for the entire authenticated + admin surface** (flagged by eng review, unresolved): if Keycloak goes down, the founder can't submit-side test, log in, toggle inventory, or triage requests — only public browse keeps working. No monitoring or break-glass admin path decided yet.
- **Public browse endpoint must not leak requester PII** (flagged by eng review, unresolved): stated as a requirement, not yet resolved with an implementation approach (e.g. a dedicated public read model that never touches the PartRequest table).

## Success Criteria

- The demand-capture MVP is live and seeded into the existing LOTR: Fate of the Fellowship BGG thread plus 2-3 similar threads/subreddits.
- Real request volume is collected (target: enough requests within a few weeks — the clock starts at the Assignment's no-code landing-page go-live, the earliest and cheapest signal-gathering point, and is evaluated cumulatively across the Assignment phase and the concierge MVP once it launches — to distinguish "a handful of unique-part asks" from "dense, repeated fungible-part demand" per the criticality-tier framing).
- At least one real transaction is completed end-to-end (request → manual fulfillment → payment) to validate willingness-to-pay net of shipping/labor. **One transaction alone cannot establish demand density or unit economics (flagged by eng review's outside voice) — it validates that the mechanics work end-to-end, not the go/no-go call itself, which depends on the aggregate request volume against the build trigger above.**
- A go/no-go read on Approach B (full automation) vs. Approach C (clearinghouse) vs. continuing the concierge model, based on real data rather than the original napkin-math assumption.

## Distribution Plan

Web application (public browse + authenticated request/admin flows). Deployment platform not yet decided in this session — global defaults point to Render via blueprint unless otherwise specified. No CI/CD pipeline exists yet; this is pre-code.

## Dependencies

- BoardGameGeek XML API access for game lookup (used in both the request form and admin inventory-add form). The BGG API is known to have asynchronous/poll-based behavior and rate limits on some endpoints — both flows need a manual free-text game-name entry fallback so a slow or unavailable lookup never blocks a request or an inventory add.
- Keycloak instance (self-hosted) configured with Google and Facebook as upstream identity providers, plus native username/password.
- A domain name (not registered yet — no rush per founder).
- One trial game purchase (used or new copy of a target title) to seed real inventory and test the flow end-to-end.

### Failure modes
- BGG API down/slow → mitigated by manual fallback (has error handling, not silent).
- Keycloak down → visible outage (login/admin fail loudly), not silent — but no monitoring yet (TODOS.md).
- Email delivery fails → **critical gap**: silent (buyer never learns the outcome), no test, no error handling, no in-app status page for v1. Acceptable at MVP volume (founder can manually check "did they reply") but worth naming plainly.
- Public browse accidentally serving PartRequest/PII data → would be silent if it happened, no test or guard yet (TODOS.md) — **critical gap** in principle, low likelihood given the tiny initial data model.

### Worktree parallelization strategy
Sequential implementation, no parallelization opportunity — this is a single small app with one shared data model; the D1 structure decision explicitly avoided independent service boundaries that would parallelize cleanly.
